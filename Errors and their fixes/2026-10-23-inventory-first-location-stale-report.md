# Inventory could upload yesterday's (and another location's) stock as the first location's file

- **Date:** 2026-10-23
- **Reported as:** found in the 23-Oct code + workflow health review ("something is broken"; review item "what happens when a location export fails mid-run"). No wrong file has been traced to it yet.
- **Symptom:** none in the logs so far - a latent hole. Inventory waits for "the newest InvViewBySkuBin row with status SUCCESS that is not in `_seen_report_ids`", and `_seen_report_ids` started EMPTY: it only ever held ids this run had downloaded itself. For the first location (the session's own, NM4) the newest row before our request is the previous run's LAST report: run 39761427312 (22-Oct) ended with `[  5s] Latest Report #1887878  Status: SUCCESS` (W03). On 23-Oct (run 39936624412) NM4 got `[  5s] Latest Report #1894872  Status: SUCCESS` - correct, because our request had registered. Had the Export click not created a request (the 10-Oct failure mode: a Vinculum modal swallowing native clicks; `export_clicked` is set as soon as `btn.click()` returns), NM4's slot would have been filled with #1887878 - yesterday's W03 stock - with no error.
- **Where:**
  - `scripts/inventory_report_to_drive.py` `main()` (no "before this run" snapshot) and step 9 `get_latest_report` / the wait loop (`if report_id and report_id in _seen_report_ids`).
  - Pick Pack (`_seen_rows` from the row before the request), Sales (`before["id"]`) and Order Enquiry (`_seen_report_ids` + request-time filter) all have a pre-request guard; Inventory was the only one without.
- **Root cause:** the stale-report guard was built for "an earlier LOCATION's report" when the location loop was added (2026-10-19), and nothing excluded reports that already existed when the run started, so for location 1 the previous run's newest report was a valid candidate.
- **Why it wasn't caught:** our own request normally appears within 5 s and has the highest id, so the hole never showed; the per-location row counts look plausible either way; no test covered the browser flow.
- **Fix:** `common/vinculum_ui.remember_latest_report(page, base, name, seen)` opens Pending Reports once after login and adds the newest existing `InvViewBySkuBin` id (page or iframe) to `_seen_report_ids`; the wait loop then treats it like an earlier location's report (keeps waiting, fails after 120 s instead of uploading stale data). It never raises (logs `[!] Could not read Pending Reports before the export` and carries on), so it cannot break a run that works today. `latest_report_js(name)` holds the JS.
- **Evidence:**
  - `python -m pytest tests/test_remember_latest_report.py -q` -> `4 passed` (newest id marked seen, grid in an iframe, no report / bad JSON / logged-out page never raise, and the JS run under node against a stub grid picks #1887878 over #1,887,852 and ignores an OrderEnquiryExport row).
  - Full suite in the commit's test run (`python -m pytest tests -q`).
  - NOT run against Vinculum (workflows were not run in this review: each run logs in and ends the user's session). First real check: the next Inventory log should show `Newest InvViewBySkuBin before this run: #<yesterday's last id> (SUCCESS) - never taken as this run's report` right after `[✓] Login successful!`.
- **Blast radius:** Inventory only (one Pending Report page visit, ~5 s, per run). A first-location export that does not register now fails the run instead of uploading stale data; with the evening catch-up run (2026-10-23-inventory-single-daily-run-lost-when-cancelled.md) that day is retried.
- **Still open:** Inventory still has no per-run retry (one failed location fails the whole run) - covered for the day by the catch-up run, not by an in-run retry.
