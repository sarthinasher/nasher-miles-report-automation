# Sales Report runs take 1.5-6 h and time out: the 17-location loop exports the same company-wide report 17 times

- **Date:** 2026-10-23
- **Reported as:** "why is there a gap in 12th to 15th October in Full Flow FMS please check and fix that". Part of the answer: the Sales back-fill for 13-20/10 (run 39716075711) was cancelled after 5 h 50 min, and every Sales run since 19-Oct takes 1 h 40 min to 6 h (several cancelled), so the Sales files for those days are missing or late.
- **Symptom:**
  - Sales runs (all on the location-loop code): 39716075711 (back-fill 13/10-20/10, dispatched 2026-10-22T03:18Z) cancelled at 09:08 after 5 h 50 min with 20/10 still in progress; 39613882104 2 h 50 min; 39572252190 2 h 14 min (cancelled); 39396241597 6 h (cancelled); 39751069123 1 h 38 min; 39792593177 1 h 45 min.
  - One date takes 34-70 min: 13/10 = 36 min 27 s for 17 exports (median 116 s per location export incl. the switch), 18/10 and 19/10 = 70 min (the 17 locations exported twice after a Drive upload error, see 2026-10-23-drive-upload-ssl-eof.md).
  - The merge log looked like A02 alone had the data: `13.10.2026: rows per location -> A02=827, A03=0, A07=0, GJ1=0, NM0=0, NM2=0, NM1=0, NM4=0, S02=0, NM3=0, S01=0, NM6=1, S03=0, NM8=0, NM7=0, NM9=0, W03=0 | total 828 (13231 duplicate row(s) seen in an earlier location dropped)`.
- **Where:** `scripts/vinculum_sales_report_to_drive.py` `_export_steps` called `common/vinculum_ui.export_all_locations` with `DEFAULT_LOCATIONS = "all"` (17 locations per date), added on 2026-10-19 (89d6fc0).
- **Root cause:** the MIS Sales Report is NOT per location: every location returns the full company-wide report. The per-export lines of run 39716075711 show the same count from every location, including the session's own location NM4 that the login lands on:
  - 13/10/2026: `NM4: 827 data row(s)`, `A02: 827 data row(s)`, `A03: 827`, ... `NM7: 827` - 17 of 17 exports = 827. 13231 dropped duplicates = 16 x 827 - 1.
  - 15/10: 26 exports, all 734. 16/10: 17 x 607. 17/10: 17 x 696. 18/10: 34 x 504. 19/10: 34 x 544. 20/10: 5 x 164 (and 34 x 164 in 39792593177). 21/10: 17 x 649 (39751069123 and 39792593177).
  - The merge credits a row to the first location in Vinculum's list (A02), not to the location that exported first (NM4), hence `A02=827 ... NM4=0`. The odd `NM6=1` / `A03=1` / `NM1=2, NM4=1` rows are rows that differ from the A02 copy, i.e. a row that changed between two exports minutes apart.
  - The 2026-10-19 record assumed Sales was per location like Pick Pack ("presumably NM4-only too (not counted)"); nobody had per-location Sales counts until these runs.
- **Why it wasn't caught:** the 17-location loop was built for Pick Pack / Order Enquiry, which really are per location, and applied to Sales without a count. Until 21-Oct the Sales merge read 0 rows from every file (2026-10-21 xlsx bug), so the first real per-location Sales counts appeared only in the 21/22-Oct logs. The `A02=827 ... others 0` line read like "A02 has all the data", hiding that every location had all of it.
- **Fix:**
  - `scripts/vinculum_sales_report_to_drive.py`: exports ONE location per date, from `SALES_LOCATION` (`DEFAULT_SALES_LOCATION = "A02"`). Logs `SALES_LOCATION=... -> export from A02 only`, `Session location after login: NM4`, `Exporting ONE location: A02 (switching from NM4)`, `A02: <n> data row(s)` and the usual `rows per location -> A02=<n> | total <n>`.
  - `SALES_LOCATION` values (`common/vinculum_ui.single_location_choice`): blank / unset = A02; a code (`NM4`, ...) = that location; `DEFAULT` (or `SESSION`) = no switch, the location the login lands on; `ALL` (or `*`) = the old loop over `VIN_LOCATIONS` + merge (escape hatch). Anything else (a list, `A 02`) fails before login with exit code 2. Blank means A02 (not "no switch") because a blank workflow input and an unset repo variable both arrive as "".
  - `common/vinculum_ui.export_one_location`: reads the Switch Location page, switches only if the session is elsewhere (no switch back: "Do Nothing" switches last for the session only; run 39751069123 logged in on NM4 right after 39716075711 was cancelled while on NM0), exports, logs the row count; a retry reuses the earlier attempt's file like `export_all_locations`. A location the user cannot switch to is a `LocationError`.
  - `.github/workflows/vinculum-sales-report.yml`: input `sales_location` (blank = repo variable `SALES_LOCATION`, else A02), env `SALES_LOCATION`; `locations` now only matters with `sales_location=ALL`. Scheduled runs: unchanged inputs, A02. Timeout stays 350 min (room for `ALL`).
  - Pick Pack / Order Enquiry / Inventory are unchanged (still `export_all_locations`).
  - No minimum-row check was added: no existing Sales row-count expectation to compare to; a "no data" answer still fails the date (`No location returned a Sales Report file`).
  - Tests: `tests/test_vinculum_ui.py` - `single_location_choice` values and rejects, one switch / no switch / no switch-back, unknown location error, retry reuse.
- **Evidence:** run 39716075711 per-export lines (`2026-10-22T03:20:22Z NM4: 827 data row(s) in VIN_REP_168_d1f8be5e-...xlsx`, `03:22:18Z A02: 827 data row(s)`, `03:24:14Z A03: 827`, ... `03:51:18Z NM7: 827`); runs 39613882104, 39751069123, 39792593177 (same pattern for 17/10, 19/10, 20/10, 21/10). Expected time with one location: login + Switch Location read ~1 min, switch ~20 s, export ~80-115 s, upload -> ~3 min per date (10 dates ~30 min, vs. 35-70 min per date before).
- **Blast radius:** Sales files uploaded by the loop may each hold 1-3 extra rows that are a second, slightly different copy of a row (13.10: NM6=1; 17.10: A03=1, NM2=1; 18.10: NM8=1; 19.10 from 39716075711: S03=1; 21.10: NM1=2, NM4=1) - not verified against the files. Every Sales run since 19-Oct held the `vinculum-session` group for hours, delaying / cancelling queued Pick Pack, Order Enquiry and Inventory runs.
